# Architecture

## 目的

本書は Shelvia のアーキテクチャの全体像を示す入口です。具体的なコマンド仕様や実装構造、テスト方針は、粒度ごとに分割した `docs/` 配下の各ドキュメントに記載します。

Shelvia は、個人の読書記録をローカルで管理するためのシンプルな CLI ツールです。永続化の対象は `shelf root` 配下の TOML ファイルのみであり、SQLite は検証済みデータから都度生成される一時的なインメモリ検索ビューとしてのみ扱います。

また、ハーネスエンジニアリングの考え方に基づき、`AGENTS.md` はインデックス (目次) として保ち、実装や設計に必要な知識は `docs/` 配下のドキュメントに集約します。エージェントや開発者がコードベースの設計思想・制約・検証方法を容易に辿れる状態を維持します。

- 参考: [OpenAI: ハーネスエンジニアリング](https://openai.com/ja-JP/index/harness-engineering/)

## 設計目標

- **プレーンテキストの維持**: Shelvia を介さずとも、任意のエディタや Git で直接閲覧・編集・差分管理できること
- **厳格なバリデーション**: データ不整合を排除し、信頼性の高い検索結果を提供すること
- **シンプルで明快な構成**: 過度な抽象化を避け、見通しの良い設計を保つこと
- **明確な境界と不変条件**: 場当たり的な条件分岐を排し、レイヤー境界とドメイン制約を明示すること
- **親切なエラー通知**: エラー発生時は、修正すべき対象ファイルと具体的な理由を示すこと

## 非目標

- 独自データベースを永続的な情報源として抱え込むこと
- 汎用的なテキスト検索ツールを代替すること
- 初期リリースにおけるプラグイン機構やクライアント・サーバー構成

## ドキュメントの役割分担

- **`README.md` / `README-ja.md`**: エンドユーザー向けドキュメント。ツールの動機、インストール、利用方法、データ形式などを簡潔に説明します (実装詳細やアーキテクチャは含めません)。
- **`docs/`**: 開発者およびエージェント向けの設計ドキュメント。アーキテクチャ、コマンド仕様、バリデーション境界、不変条件を定義します。
- **`AGENTS.md`**: リポジトリ全体のナビゲーション目次。詳細な手順書ではなく、参照すべき各ドキュメントへのポインタとして機能させます。

## アーキテクチャ方針

Shelvia は **Clean Architecture** を基盤とし、外部境界の抽象化には **Hexagonal Architecture (Ports and Adapters)** のパターンを採用します。

- **内側への単方向依存**: 依存関係は常に「外側 (CLI, localfs, queryengine, presentation)→ アプリケーション層 → ドメイン層」の順とし、ドメイン層は外部の詳細を一切知りません。
- **Ports & Adapters による外部境界の分離**: CLI、ローカルファイルシステム、クエリエンジン (SQLite)、端末出力など、差し替えや独立テストが必要な境界をポート (インターフェース) として定義します。

## 不変条件 (Invariants)

今後の機能拡張やリファクタリングにおいても、以下のルールを厳格に維持します。

1. **永続化は TOML のみ**: データの永続化は TOML ファイルのみで行い、DB ファイルを永続化しない。
2. **SQLite は単方向の一時ビュー**: SQLite は TOML から検証を経て構築される読み取り専用の一時ビューであり、SQLite 側の変更を TOML に逆流させない。
3. **投入前のドメイン検証**: クエリエンジンへのデータ投入前に、必ずドメインバリデーションを完了させる。
4. **ファイルパスを伴うエラー診断**: ファイル由来のエラーメッセージには、ユーザーが特定・修正できるファイルパスと位置を含める。
5. **Clean Architecture の依存規則の遵守**: ドメイン層およびアプリケーション層は、具象アダプターや外部ライブラリに依存しない。
6. **ユーザー向けドキュメントの同期**: `README.md` と `README-ja.md` は常に挙動・仕様を同期させる。
7. **`AGENTS.md` の簡潔性の維持**: 詳細な設計知識は `docs/` 配下に置き、`AGENTS.md` は目次として保つ。
